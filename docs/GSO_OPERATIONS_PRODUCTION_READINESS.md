## What OPS-2 adds on top of the approved overnight architecture

| Area | Before (OPS-1) | Now (OPS-2) |
|---|---|---|
| Intent persistence | in-memory singleton | `ActionIntentRepository` boundary; Memory + Prisma implementations; `GSO_OPS_REPOSITORY` selects |
| Audit | array on the intent | append-only `OpsActionAuditEvent` rows with every required field (intent, key, agent, version, provider, model, entity, action, reason, payload keys, level, prev/new state, actor, approver, time, result, external ref, error) |
| External events | process deduper | `OpsExternalEventReceipt` (unique source+externalId); Slack events and clicks claimed before any work |
| Outbox | documented | `OpsOutboxMessage` PENDING→PROCESSING→COMPLETED / FAILED(retry) / DEAD; idempotent enqueue; exclusive claim; bounded backoff; stale-claim release |
| Worker | none | `processOutboxBatch` — claims, revalidates intent approval, honours kill switch, executes through the intent engine, retries, deads |
| Production writes | advisory guard | `requestProductionTransition` — the ONE path: intent approved → kill switch → job/status → guard with real facts → routing → single execution → audit |
| Kill switches | none | `GSO_AGENT_EXECUTION_ENABLED` (consequential execution) and `GSO_AGENT_REASONING_ENABLED` (LLM), both default false, independent |
| Reasoning | none | provider boundary; OpenAI runtime prepared and disabled; fake/disabled providers; tool gateway; structured outputs; HITL mapping |
| Slack | memory store, JSON-only API calls | repository-backed approvals with receipts; read methods form-encoded (private channel discovery fixed); `findChannel` |
| Hub | registry/matrix | provider + kill-switch status, grouped durable intents, outbox, paused runs |
| MOQ | sales rule said 100 | sticker bags 50 everywhere; parity test |

## Worker scheduling (owner-gated)

Render has no cron in this repo and no worker service. Options: (a) Render Cron Job (paid tier) invoking `processOutboxBatch` via a small script; (b) Render Background Worker (paid) running a loop that also hosts Socket Mode; (c) an authenticated HTTP endpoint hit by an external scheduler the owner already owns. None is configured. Without a worker the outbox simply accumulates PENDING rows; nothing is lost and nothing executes.

## Rollback

Reverting the application alone is sufficient at every phase: the new tables are unread by pre-OPS-2 code; `GSO_AGENT_REASONING_ENABLED=false` removes the model; `GSO_AGENT_EXECUTION_ENABLED=false` freezes execution with intents preserved for audit.

## Safest deployment sequence

1. Owner reviews branch, docs, simulation output, sandbox evidence.
2. Merge; deploy with no new env vars (routes inert, memory repository, everything off).
3. Owner applies the OPS-2 migration (`prisma migrate deploy`); set `GSO_OPS_REPOSITORY=prisma`; verify hub.
4. Slack: `SLACK_SIGNING_SECRET`, `SLACK_BOT_TOKEN`, `SLACK_TEST_CHANNEL`, staff identities (table or `SLACK_STAFF_MAP`); Interactivity URL → `/api/slack/interactions`; keep `SLACK_SANDBOX_ONLY=true`.
5. Worker: owner chooses a scheduling option; run the worker with `GSO_AGENT_EXECUTION_ENABLED=false` first (Slack notices only).
6. OpenAI: follow `GSO_OPENAI_AGENTS_RUNTIME.md` enablement (configured → opt-in live test → reasoning on, execution off).
7. Only then: `GSO_AGENT_EXECUTION_ENABLED=true`, one approved action type at a time, starting with move_production_job under staff approval.
